### P1 — 반복 가능한 PR 검증

현재 저장소에 `.github/workflows` 검증 파이프라인이 없습니다. P0 복구 후 설치 고정 → 타입 → 린트 → 테스트 → 빌드를 PR에서 실행합니다. CI에 실사용 DB 키를 넣지 않고 SQL 테스트는 별도 검증 DB에 연결합니다.

완료 조건: 새 PR의 검사 결과를 링크로 확인할 수 있고, 실패한 검사를 통과한 것처럼 보고하지 않음. 빌드는 폰트/네트워크 요구사항도 확인.

### P1 — 실제 API까지 검증하는 사용자 흐름

현재 `pnpm test`는 로직 테스트이며 SQL 테스트와 브라우저 확인은 별도입니다. 모의 API만 통과하면 실제 RLS/RPC까지 검증한 것은 아닙니다.

우선 자동화할 흐름: 로그인 → 훈련 → 오프라인 답변/재접속 → 중복 없는 저장 → 오답의 P 추가 → 수정 충돌 → 삭제/취소. 두 계정의 데이터 분리도 검증합니다.

완료 조건: 별도 테스트 사용자/DB로 반복 실행하고 실사용 데이터 변경 없이 실패 원인을 UI/API/DB 중 어디인지 찾을 수 있음.

## 다음 단계의 구조 개선

### P1 — UI 일관성을 기능 단위로 확장

개인 단어장과 오답노트는 공통 StageFilter/Modal을 쓰지만 헤더·검색·빈 상태·페이지 이동은 여전히 기능별 구현입니다. 대시보드/에디터의 스타일도 다릅니다.

제안: 실제로 반복되는 헤더/검색/페이지 이동부터 작은 공통 UI로 추출. 모바일 320px, 긴 일본어/한국어, 키보드, 다크 모드에서 확인합니다. 서로 다른 기능을 하나의 거대한 범용 목록으로 합치지 않습니다.

### P1 — 검색 범위와 방식 일치

오답노트는 최근 100개 안에서 브라우저 검색이며 가나/반각 정규화를 합니다. 내 단어장은 전체 소유 단어를 DB에서 검색합니다. 범위와 매칭 규칙이 서로 다릅니다.

제안: 검색 범위는 짧은 접근성 설명으로 알리고, 히라가나/가타카나·반각·한글 발음 매칭 기준을 합의해 동일 입력의 결과 차이를 테스트합니다. 개인 단어 전체를 브라우저로 내려받아 해결하지 않습니다.

### P2 — 구조 경계를 테스트로 지키기

학습 엔진, 저장 조정, Phaser 표현은 이미 분리되어 있습니다. 이 경계를 문서만으로 유지하면 새 기능에서 다시 섞일 수 있습니다.

제안: 학습 엔진의 React/Phaser 의존 금지, 서버 전용 모듈의 클라이언트 유입 방지를 린트/구조 검사로 추가. 대형 파일은 규칙·부수효과·표현 책임을 기준으로 쪼갭니다. 줄 수만으로 파일을 늘리지 않습니다.

### P2 — 요청/오류 관찰 가능성

API가 `load_failed` 등으로 오류를 단순화하므로 클라이언트만 보면 원인을 좁히기 어렵습니다. 코드 검토만으로 실제 응답 시간이나 장애 빈도를 알 수는 없습니다.

제안: 개인정보 없는 요청 ID·API 시간·DB 호출 수·큐 길이·재시도 원인을 수집. 브라우저/API/DB 시간을 나눠 기준선을 만든 뒤 성능 목표를 결정합니다. 사용자 단어/토큰 원문 수집은 제외합니다.

### P2 — 문장 훈련을 별도 제품 흐름으로 정리

문장 콘텐츠·후보와 단어 학습 엔진은 별도 모듈입니다. 현재 구현에서 저장/복습을 공유한다고 가정할 수 없습니다.

제안: 문장 출제 범위, 정답 허용 기준, 설명 표시, 진도 저장 여부를 먼저 문서화. 공통 단어 연결과 학습 기록 통합은 데이터 계약부터 설계합니다. 다른 작업의 미커밋 문장 변경은 이번 정리에 포함하지 않았습니다.
